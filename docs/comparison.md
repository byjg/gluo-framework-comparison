# Feature by feature

How each part of the application is done, with the code that is actually in this
repository. For the commands that produced it, see the step-by-step guides:
[gluo.md](gluo.md), [laravel.md](laravel.md), [symfony-official.md](symfony-official.md),
[symfony.md](symfony.md), [cakephp.md](cakephp.md) and [codeigniter.md](codeigniter.md).

Symfony is built twice. `symfony-official/` uses official packages only;
`symfony/` uses the community Docker template and a community soft-delete bundle. They
share the login, the generated CRUD, the validation, the routes, the screens and the
tests, so the Symfony column below describes both. Where they differ — creating the
project, timestamps and soft delete, Docker — the text says so, and
[section 14](#14-the-two-symfony-builds) puts the two side by side.

## 1. Architecture

| | Gluo | Laravel | Symfony | CakePHP | CodeIgniter |
|---|---|---|---|---|---|
| Shape | REST API + separate SPA | one application | one application | one application | one application |
| Frontend | React 19 + Vite, own container | React 19 through Inertia, same app | Twig, server-rendered | PHP templates, server-rendered | PHP views, server-rendered |
| Auth state | JWT in the browser, sent as `Authorization: Bearer` | session cookie | session cookie | session cookie | session cookie |
| Reusable from another client | yes, it is an API | no, the endpoints return Inertia pages | no, the endpoints return HTML | no, the endpoints return HTML | no, the endpoints return HTML |
| Containers | API, frontend, MySQL | app, MySQL | official: MySQL, mail catcher (PHP on the host). template: app, MySQL, mail catcher | MySQL (PHP on the host) | MySQL (PHP on the host) |

Gluo is the only one where the backend is a documented API that another client (mobile
app, another service) could call as is.

## 2. Creating the project

| | Command | Questions asked |
|---|---|---|
| **Gluo** | `composer create-project byjg/gluo gluo ^7.0 --stability=dev` | namespace, database, keep frontend, keep examples — or all from `setup.json` |
| **Laravel** | `composer create-project laravel/react-starter-kit laravel --stability=dev` | which auth features to keep |
| **Symfony** (official) | `composer create-project symfony/skeleton`, `composer require webapp` (or `symfony new --webapp`) | whether Flex should write Docker configuration |
| **Symfony** (template) | `git clone dunglas/symfony-docker`, `docker compose up`, `composer require webapp` | none; the choices are the packages you require |
| **CakePHP** | `composer create-project cakephp/app cakephp` | none; it writes `config/app_local.php` and a security salt |
| **CodeIgniter** | `composer create-project codeigniter4/appstarter codeigniter` | none; `shield:setup` later asks for the sender e-mail and whether to migrate |

Friction found while building:

- **Gluo** — `--stability=dev` is required until 7.0 is tagged.
- **Laravel** — the tagged starter kit is an old Laravel 12 one, so `--stability=dev` is
  required here too; the installer needs Node next to PHP.
- **Symfony** (official) — no problem creating the project. The database service Flex
  writes is PostgreSQL, so MySQL is a three-file manual switch.
- **Symfony** (template) — the Docker template did not start with the current FrankenPHP
  image until one Mercure setting was changed, and it also defaults to PostgreSQL: a
  four-file manual switch.
- **CakePHP** — no problem creating the project, but no Docker setup: a compose file for
  MySQL is written by hand, and the datasource points to it.
- **CodeIgniter** — no problem creating the project, and no Docker setup either. The
  `.env` starts as a commented template (`env`), and the global CSRF filter ships turned
  off.

## 3. Login

| | Gluo | Laravel | Symfony | CakePHP | CodeIgniter |
|---|---|---|---|---|---|
| Where it comes from | shipped with the starter | shipped with the starter kit | generated by two maker commands | official Authentication plugin | official Shield package, installed by `shield:setup` |
| Mechanism | `POST /login` returns a JWT | Fortify session login | `form_login` authenticator | Session + Form authenticators | session authenticator |
| Code you write | none | none | none | ~70 lines: the service, the middleware, the component, a `UsersController` with login and logout, the login template, password hashing in the entity | none |
| Also included | token refresh, password reset by e-mail code, roles | registration, e-mail verification, password reset, 2FA, passkeys | logout | logout (written by you) | registration, login by e-mail link, groups and permissions, remember-me, logout |

**Gluo** — `src/Controller/LoginController.php` is a thin class over the core; the route,
the request schema and the validation are attributes:

```php
#[OA\Post(path: "/login", tags: ["Login"])]
#[OA\RequestBody(...)]          // username + password
#[ValidateRequest]
public function post(HttpResponse $response, HttpRequest $request): void
{
    parent::post($response, $request);
}
```

**Laravel** — there is no login controller in the project; Fortify owns the routes and
the project only says which page renders the form (`app/Providers/FortifyServiceProvider.php`):

```php
Fortify::loginView(fn (Request $request) => Inertia::render('auth/login', [...]));
```

**Symfony** — `make:security:form-login` writes a controller that only shows the form;
the firewall does the authentication (`config/packages/security.yaml`):

```yaml
firewalls:
    main:
        provider: app_user_provider
        form_login:
            login_path: app_login
            check_path: app_login
            enable_csrf: true
            default_target_path: app_product_index
        logout:
            path: app_logout
```

**CakePHP** — the plugin does the authentication; the application builds the service in
`src/Application.php` and writes the two actions:

```php
$service->loadAuthenticator('Authentication.Session');
$service->loadAuthenticator('Authentication.Form', [
    'fields' => ['username' => 'email', 'password' => 'password'],
    'loginUrl' => Router::url('/users/login'),
]);

// src/Controller/UsersController.php
public function login(): ?Response
{
    $result = $this->Authentication->getResult();
    if ($result?->isValid()) {
        return $this->redirect($this->Authentication->getLoginRedirect() ?? '/products');
    }
    // ...
}
```

**CodeIgniter** — `shield:setup` adds one line to `app/Config/Routes.php`, which brings the
login, registration, e-mail link and logout routes, controllers and views:

```php
service('auth')->routes($routes);
```

## 4. Protecting the screens

**Gluo** — per endpoint, as an attribute, with roles available out of the box:

```php
#[RequireAuthenticated]              // any valid token: get, list
#[RequireRole(User::ROLE_ADMIN)]     // admin only: create, update, delete
```

On the SPA side the route sits inside `<ProtectedLayout>`, which redirects to `/login`
when there is no valid token.

**Laravel** — per route group, in `routes/web.php`:

```php
Route::middleware(['auth', 'verified'])->group(function () {
    Route::resource('products', ProductController::class)->except('show');
});
```

**Symfony** — by URL pattern, in `config/packages/security.yaml`:

```yaml
access_control:
    - { path: ^/login, roles: PUBLIC_ACCESS }
    - { path: ^/, roles: ROLE_USER }
```

**CakePHP** — every action, through the component loaded in `AppController`; a
controller lists the actions a guest may open:

```php
// src/Controller/AppController.php
$this->loadComponent('Authentication.Authentication');

// src/Controller/UsersController.php
$this->Authentication->allowUnauthenticated(['login']);
```

**CodeIgniter** — by route, with Shield's `session` filter:

```php
$routes->presenter('products', ['controller' => 'ProductController', 'except' => 'show,remove', 'filter' => 'session']);
```

The builds keep their framework's default, so they do not enforce the same rule:

| | Read (get, list) | Write (create, update, delete) |
|---|---|---|
| Gluo | any logged-in user | **admins only** — what codegen generates |
| Laravel | any logged-in, verified user | any logged-in, verified user |
| Symfony | any user with `ROLE_USER` | any user with `ROLE_USER` |
| CakePHP | any logged-in user | any logged-in user |
| CodeIgniter | any logged-in user | any logged-in user |

The seed user is an admin, so the difference does not show when you try the builds. To
make them match, change one side:

- **Let every logged-in user write in Gluo:** replace `#[RequireRole(User::ROLE_ADMIN)]`
  with `#[RequireAuthenticated]` on `postProduct`, `putProduct` and `deleteProduct`.
- **Make writing admin-only in Laravel:** a `ProductPolicy` whose `create`, `update` and
  `delete` check the role, and `$this->authorize(...)` in the actions (or `->can(...)` on
  the routes).
- **Make writing admin-only in Symfony:** `#[IsGranted('ROLE_ADMIN')]` on `new`, `edit` and
  `delete`, or an `access_control` rule for those paths.
- **Make writing admin-only in CakePHP:** the official Authorization plugin
  (`cakephp/authorization`) with a `ProductPolicy`, and `$this->Authorization->authorize()`
  in `add`, `edit` and `delete`.
- **Make writing admin-only in CodeIgniter:** Shield's group filter on those routes
  (`'filter' => 'group:admin'`), or `auth()->user()->inGroup('admin')` in the actions.

Gluo is the only build where reading and writing have different permissions without
extra work.

## 5. Migration

| | Gluo | Laravel | Symfony | CakePHP | CodeIgniter |
|---|---|---|---|---|---|
| Written in | SQL | PHP schema builder | SQL, generated | PHP table API (Phinx-style) | PHP, with Forge |
| Who writes it | you | you | `make:migration`, by diffing entities against the database | `bake migration`, from the column list you type | you |
| Rollback | a second SQL file you write | `down()` you write (generated for a new table) | `down()` generated | none to write: `change()` is reversible | `down()` you write |
| Date columns | in the SQL you write | `timestamps()` + `softDeletes()` | from the entity fields (official: generated by `make:entity`; template: from the bundle's traits) | on the command line, like the other columns | in the Forge array you write |
| Run | `php gluo --env=dev migrate:update` | `artisan migrate` | `doctrine:migrations:migrate` | `bin/cake migrations migrate` | `php spark migrate` |

**Gluo** — `db/migrations/up/00001-create-table-product.sql`:

```sql
create table product
(
    id int auto_increment not null primary key,
    name varchar(100) not null,
    price decimal(10,2) not null,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted_at DATETIME NULL
) ENGINE=InnoDB;
```

**Laravel** — `database/migrations/*_create_products_table.php`:

```php
Schema::create('products', function (Blueprint $table) {
    $table->id();
    $table->string('name', 100);
    $table->decimal('price', 10, 2);
    $table->timestamps();
    $table->softDeletes();
});
```

**Symfony** — nothing is written; the generated migration contains:

```php
$this->addSql('CREATE TABLE product (id INT AUTO_INCREMENT NOT NULL, name VARCHAR(100) NOT NULL,
    price NUMERIC(10, 2) NOT NULL, created_at DATETIME NOT NULL, updated_at DATETIME NOT NULL,
    deleted_at DATETIME DEFAULT NULL, PRIMARY KEY (id)) DEFAULT CHARACTER SET utf8mb4');
```

**CakePHP** — `config/Migrations/*_CreateProducts.php`, written by `bake migration` from
`'name:string[100]' 'price:decimal[10,2]' 'created_at:datetime' 'updated_at:datetime' 'deleted_at:datetime?'`:

```php
$table = $this->table('products');
$table->addColumn('name', 'string', ['default' => null, 'limit' => 100, 'null' => false]);
$table->addColumn('price', 'decimal', ['default' => null, 'null' => false, 'precision' => 10, 'scale' => 2]);
$table->addColumn('created_at', 'datetime', ['default' => null, 'null' => false]);
$table->addColumn('updated_at', 'datetime', ['default' => null, 'null' => false]);
$table->addColumn('deleted_at', 'datetime', ['default' => null, 'null' => true]);
$table->create();
```

**CodeIgniter** — `app/Database/Migrations/*_ProductMigration.php`, generated empty by
`make:scaffold` and filled in:

```php
$this->forge->addField([
    'id'         => ['type' => 'INT', 'unsigned' => true, 'auto_increment' => true],
    'name'       => ['type' => 'VARCHAR', 'constraint' => 100],
    'price'      => ['type' => 'DECIMAL', 'constraint' => '10,2'],
    'created_at' => ['type' => 'DATETIME', 'null' => true],
    'updated_at' => ['type' => 'DATETIME', 'null' => true],
    'deleted_at' => ['type' => 'DATETIME', 'null' => true],
]);
$this->forge->addPrimaryKey('id');
$this->forge->createTable('products');
```

The source of truth differs: the **table** in Gluo, the **migration** in Laravel and
CodeIgniter, the **entity class** in Symfony. CakePHP sits in between: the command line
writes the migration, and from then on bake reads the **table**.

## 6. Model

| | Gluo | Laravel | Symfony | CakePHP | CodeIgniter |
|---|---|---|---|---|---|
| ORM | MicroOrm | Eloquent | Doctrine ORM | CakePHP ORM | Model + Query Builder |
| Pattern used here | ActiveRecord | ActiveRecord | Data Mapper + Repository | Table (repository) + Entity | Model (table gateway) |
| Fields declared in the class | yes, generated | no, read from the table at runtime | yes, generated | no, read from the table at runtime (listed in a generated docblock) | no; `$allowedFields` lists the writable ones |
| Accessors | generated | magic properties | generated | magic properties | none; rows are arrays (`$product['name']`) |
| File size | 118 lines, 1 edited by hand | 16 lines, 2 written by hand | official: 114 lines, ~15 by hand. template: 63 lines, 7 by hand | Table 71 + Entity 33 lines, ~10 edited by hand | 49 lines, 6 edited by hand |
| Type and length of each field | yes: `OA\Property(type, format, maxLength)`, generated from the column | no; they are in the migration | yes: `ORM\Column(length, precision, scale)`, generated | the length, as `maxLength` in the baked validation | no; they are in the migration |
| Allowed range of a value | yes: `OA\Property(maximum, minimum)`, by hand | no; it is in the `FormRequest` | yes: `Assert\Range`, by hand | yes: `greaterThanOrEqual` / `lessThanOrEqual`, by hand | yes: `$validationRules`, by hand |
| Required fields | yes: `OA\Schema(required: [...])`, generated from `NOT NULL` | no; `required` in the `FormRequest` | yes: `Assert\NotBlank`, by hand | yes: `requirePresence` + `notEmptyString`, baked from `NOT NULL` | yes: `required` in `$validationRules`, by hand |
| The same declaration validates requests | yes | — | yes (through the form) | yes (`patchEntity()`) | yes (every `insert()` / `update()`) |
| The same declaration is published to API clients | yes, as the OpenAPI schema | — | no | no | no |

### Model patterns each one supports

| | Gluo (MicroOrm) | Laravel (Eloquent) | Symfony (Doctrine) | CakePHP (ORM) | CodeIgniter (Model) |
|---|---|---|---|---|---|
| ActiveRecord | yes: `use ActiveRecord` on the model, then `Product::get($id)`, `$product->save()` | yes, and it is the only built-in pattern | no | no; entities do not save themselves | no; the model saves arrays or entities |
| Repository | yes: Model + Repository + Service, bound in the DI config. The model's attributes build a Data Mapper, which both patterns use ([Choosing a Pattern](https://opensource.byjg.com/docs/php/micro-orm/patterns)) | not built in; you write the layer yourself on top of Eloquent | yes, with Data Mapper: plain entities, the `EntityManager` persists them, one repository class per entity for queries | yes: the `ProductsTable` finds and saves `Product` entities | a table gateway rather than a repository: one `Model` per table, with the queries and the rules |
| Choice per entity | yes, both can be used in the same project | — | — | — | — |
| Generator | both: `php gluo codegen:all` writes the Repository pattern, `--activerecord` the other | `make:model` (ActiveRecord) | `make:entity` writes the entity and its repository | `bake model` writes the table and the entity, from the database | `make:model` (empty) |
| Layers in a generated CRUD | ActiveRecord: Controller -> Model. Repository: Controller -> Service -> Repository -> Model | Controller -> Model | Controller -> EntityManager / Repository -> Entity | Controller -> Table -> Entity | Controller -> Model |
| Files for one entity | ActiveRecord: 2. Repository: 4, plus 2 DI bindings | 1 model (+ controller) | 2 (entity, repository) (+ controller) | 2 (table, entity) (+ controller) | 1 model (+ controller) |

- **ActiveRecord** — the object saves and loads itself. Least code, and the model is tied
  to the database, which is fine for plain CRUD.
- **Repository** — the model is data only; a separate class talks to the database, and
  in Gluo a service holds the business rules between the controller and the repository.
  More files, easier to test and to grow.
- **Data Mapper** — Doctrine's version of the same separation: the entity knows nothing
  about persistence, and the `EntityManager` tracks changes and writes them on `flush()`.

Gluo is the only one of the five where this is a choice, per entity, with a generator
for both. Laravel gives you ActiveRecord, Symfony gives you Data Mapper, CakePHP a table
class per table with entities, and CodeIgniter a model per table; moving away from any of
them means writing the other pattern by hand.

In Gluo the choice is made when the code is generated, not in a configuration setting:
the two patterns produce a different model and a different controller. The endpoints
and the generated test are the same in both, so the API does not change. Switching an
entity later is a regeneration:

```bash
# ActiveRecord -> Repository: add the two layers and replace the controller
php gluo --env=dev codegen:repository --table=product --save
php gluo --env=dev codegen:service    --table=product --save
php gluo --env=dev codegen:controller --table=product --save

# Repository -> ActiveRecord: replace the model and the controller,
# then delete the repository, the service and their DI bindings
php gluo --env=dev codegen:model      --table=product --activerecord --save
php gluo --env=dev codegen:controller --table=product --activerecord --save
```

`--save` overwrites the controller, so hand edits to it (here, the delete endpoint and
the price range) have to be applied again. Without `--save` the code is printed instead of
written, which is a way to look at the other pattern before deciding.

This comparison uses ActiveRecord for Gluo because it is the smallest version of the
same feature.

### The model in each project

**Gluo** — `src/Model/Product.php`. Each field carries two attributes: `FieldAttribute`
maps it to the column, and `OA\Property` declares its type, length and range. Everything
is as `codegen` wrote it, including `maxLength: 100` and `minLength: 1` taken from
`varchar(100) not null`, except the price range, which was added by hand:

```php
#[OA\Schema(required: ["id", "name", "price"], type: "object", xml: new OA\Xml(name: "Product"))]
#[TableAttribute("product")]
class Product
{
    use ActiveRecord;
    use OaCreatedAt;
    use OaUpdatedAt;
    use OaDeletedAt;

    #[OA\Property(type: "integer", format: "int32")]
    #[FieldAttribute(primaryKey: true, fieldName: "id")]
    protected int|null $id = null;

    #[OA\Property(type: "string", format: "string", maxLength: 100, minLength: 1)]
    #[FieldAttribute(fieldName: "name")]
    protected string|null $name = null;

    #[OA\Property(type: "number", format: "double", maximum: 99999999.99, minimum: 0)]
    #[FieldAttribute(fieldName: "price")]
    protected float|null $price = null;
    // + getters and setters
}
```

**Laravel** — `app/Models/Product.php`, complete:

```php
#[Fillable(['name', 'price'])]
class Product extends Model
{
    use HasFactory, SoftDeletes;
}
```

**Symfony** — `src/Entity/Product.php`, template build (the official build declares the
three date fields itself instead of the two traits; see [section 7](#7-timestamps-and-soft-delete)):

```php
#[ORM\Entity(repositoryClass: ProductRepository::class)]
#[Gedmo\SoftDeleteable]
class Product
{
    use TimestampableEntity;
    use SoftDeleteableEntity;

    #[ORM\Column(length: 100)]
    #[Assert\NotBlank]
    #[Assert\Length(max: 100)]
    private ?string $name = null;

    #[ORM\Column(type: Types::DECIMAL, precision: 10, scale: 2)]
    #[Assert\NotBlank]
    #[Assert\Range(min: 0, max: 99999999.99)]
    private ?string $price = null;
    // + id, getters and setters
}
```

**CakePHP** — `src/Model/Table/ProductsTable.php`, as bake wrote it from the table, plus
the two behaviors and the price range added by hand (the validation is shown in
[9. Validation](#9-validation)):

```php
public function initialize(array $config): void
{
    parent::initialize($config);

    $this->setTable('products');
    $this->setDisplayField('name');
    $this->setPrimaryKey('id');

    $this->addBehavior('Timestamp', [
        'events' => ['Model.beforeSave' => ['created_at' => 'new', 'updated_at' => 'always']],
    ]);
    $this->addBehavior('Muffin/Trash.Trash', ['field' => 'deleted_at']);
}
```

and `src/Model/Entity/Product.php`, which only says which fields a form may set:

```php
protected array $_accessible = [
    'name' => true,
    'price' => true,
];
```

**CodeIgniter** — `app/Models/ProductModel.php`, generated with every setting at its
default; these are the lines changed:

```php
protected $useSoftDeletes   = true;
protected $allowedFields    = ['name', 'price'];
protected $useTimestamps    = true;
protected $validationRules  = [
    'name'  => 'required|max_length[100]',
    'price' => 'required|decimal|greater_than_equal_to[0]|less_than_equal_to[99999999.99]',
];
```

The Gluo model and the Symfony entity carry the same kind of information: the type and
length of each field, which fields are required, and the range a value may take. In
both, the length comes from the generator and the range is written by hand. They differ
in what the declaration is used for. Symfony's `ORM\Column` drives the SQL of the
migration and `Assert\*` drives form validation. Gluo's `OA\Property` drives request
validation and is also the schema published in the OpenAPI document; the column's
precision and scale stay in the SQL migration. Laravel's model declares none of it: the
types are in the migration and the rules in the `FormRequest`. CakePHP and CodeIgniter
keep the rules next to the model — in the table class and in the model — and the types
in the migration.

## 7. Timestamps and soft delete

| | Gluo | Laravel | Symfony (official) | Symfony (template) | CakePHP | CodeIgniter |
|---|---|---|---|---|---|---|
| Built in | yes | yes | timestamps: lifecycle callbacks. Soft delete: no | no — `stof/doctrine-extensions-bundle` (community) | timestamps: yes (Timestamp behavior). Soft delete: no — `muffin/trash` (community) | yes, both |
| Turned on by | codegen, when it sees the three columns | `timestamps()` + `softDeletes()` in the migration, `SoftDeletes` trait | 3 generated fields, 2 callbacks, 1 line in the delete action, a 21-line SQL filter, 1 YAML block | 2 traits + 1 attribute on the entity, 2 YAML blocks | 2 behaviors in the table class (the Timestamp one told the column names), 1 plugin loaded | `$useTimestamps = true` and `$useSoftDeletes = true` on the model |
| Who sets the dates | the database (`DEFAULT` / `ON UPDATE`) and the trait | Eloquent | your callbacks | the bundle's listener | the Timestamp behavior | the model |
| Deleted rows hidden | automatically | automatically | by the filter you wrote | once the bundle's filter is enabled | automatically, by the Trash behavior (`find('withTrashed')` shows them) | automatically (`withDeleted()` shows them) |
| Code you own | none | none | all of it | none | none | none |

Gluo, Laravel and CodeIgniter need nothing beyond naming the columns (and, in
CodeIgniter, two settings). CakePHP has timestamps but no soft delete of its own; this
build uses the community plugin most CakePHP projects use, in the same role Gedmo plays
for Symfony. Symfony and Doctrine have no
soft delete, so there are two ways to get it.

**Official packages only** — `symfony-official/`. The dates use Doctrine lifecycle
callbacks, and deleting becomes "set the date" plus a Doctrine SQL filter:

```php
#[ORM\HasLifecycleCallbacks]
class Product
{
    #[ORM\PrePersist]
    public function onCreate(): void
    {
        $this->createdAt = $this->updatedAt = new \DateTimeImmutable();
    }

    #[ORM\PreUpdate]
    public function onUpdate(): void
    {
        $this->updatedAt = new \DateTimeImmutable();
    }
}

// src/Controller/ProductController.php, in the generated delete()
$product->setDeletedAt(new \DateTimeImmutable());

// src/Doctrine/SoftDeleteFilter.php
class SoftDeleteFilter extends SQLFilter
{
    public function addFilterConstraint(ClassMetadata $targetEntity, string $targetTableAlias): string
    {
        if (!$targetEntity->hasField('deletedAt')) {
            return '';
        }

        return sprintf('%s.%s IS NULL', $targetTableAlias, $targetEntity->getColumnName('deletedAt'));
    }
}
```

**Community bundle** — `symfony/`. Two traits and an attribute on the entity (shown in
[6. Model](#6-model)) and this configuration:

```yaml
# config/packages/stof_doctrine_extensions.yaml
stof_doctrine_extensions:
    orm:
        default:
            timestampable: true
            softdeleteable: true

# config/packages/doctrine.yaml, under doctrine.orm
filters:
    softdeleteable:
        class: Gedmo\SoftDeleteable\Filter\SoftDeleteableFilter
        enabled: true
```

The bundle is less code and is what most Symfony projects use; the official-only route
adds about 35 lines you maintain yourself. Both pass the same soft-delete test.

## 8. CRUD controller

| | Gluo | Laravel | Symfony | CakePHP | CodeIgniter |
|---|---|---|---|---|---|

**Symfony** — the `#[Assert\...]` attributes shown in [6. Model](#6-model).

**CakePHP** — `validationDefault()` in `src/Model/Table/ProductsTable.php`. The `name`
rules and the presence of `price` are as bake read them from the table; the range is the
hand-written part:

```php
$validator
    ->scalar('name')
    ->maxLength('name', 100)
    ->requirePresence('name', 'create')
    ->notEmptyString('name');

$validator
    ->decimal('price')
    ->requirePresence('price', 'create')
    ->notEmptyString('price')
    ->greaterThanOrEqual('price', 0)
    ->lessThanOrEqual('price', 99999999.99);
```

**CodeIgniter** — the `$validationRules` shown in [6. Model](#6-model).

All five end up enforcing the same rules: a name that is not empty and has at most 100
characters, and a price between 0 and 99999999.99, both required.

Gluo takes the types, the required fields, `maxLength` and `minLength` from the table when
it generates the code: `name` is `varchar(100) not null` with no default, so it gets
`maxLength: 100, minLength: 1`, and an empty name is refused like a missing one, as
Laravel's `required`, Symfony's `NotBlank`, CakePHP's `notEmptyString` and CodeIgniter's
`required` do. A range cannot be read from a column type, so `minimum` and `maximum` are
added by hand, the same as `min`/`max` in Laravel, `Assert\Range` in Symfony, the two
comparison rules in CakePHP and `greater_than_equal_to`/`less_than_equal_to` in
CodeIgniter. CakePHP's bake is the only other generator that reads the length and the
`NOT NULL` from the table.

The test sends each invalid payload to the server, on both `POST` and `PUT`: a 101-character
name, an empty name, a negative price, a price above the range and a missing `name` are
each answered with 400, and the table is unchanged. The requests are sent without the
OpenAPI spec on the client side; otherwise the test client itself would refuse them and
the server would never be exercised.

The same schema is what Swagger UI publishes, so the documented limits and the enforced
ones cannot drift apart.

### HTTPS in development

- **Gluo** — the frontend container serves HTTPS as well as HTTP. Its web server,
  `byjg/static-httpserver`, creates a self-signed certificate when it starts and listens
  on 8443, published as https://localhost:7443; mounting `cert.pem` and `key.pem` at
  `/certs` replaces it with a real one. The API container is plain HTTP on :8080, and that
  is the address the frontend calls.
- **Laravel** — Sail serves plain HTTP. This build runs on http://localhost:8081 and
  nothing was added for HTTPS.
- **Symfony, template** — FrankenPHP (Caddy) serves the whole application over HTTPS by
  default, with certificates from its own local certificate authority. This build turns
  that off (`SERVER_NAME=:80`) to keep plain HTTP on :8082 next to the other projects.
- **Symfony, official** — PHP's built-in server, used here, has no HTTPS. Symfony's
  documentation describes TLS support in `symfony server:start`, which was not used in
  this build.

- **CakePHP** and **CodeIgniter** — `bin/cake server` and `php spark serve` wrap PHP's
  built-in server, which has no HTTPS.

So two of the setups come with HTTPS without any work: Gluo for the frontend, and the
Symfony Docker template for the whole application.

## 14. The two Symfony builds

Laravel's starter kit, Sail and Eloquent's soft delete are all first-party, and Gluo
ships its own Docker files and soft-delete trait, so one build of each is "official"
by construction. Symfony is the one where following the documentation leads outside

  a list. In Gluo the list is the generated OpenAPI file (and Swagger UI); in Symfony it
  is `bin/console debug:router`, and in CakePHP `bin/cake routes`, since its CRUD is
  reached through the fallback convention rather than declared routes.
- **Who controls autowiring.** Gluo, Laravel and Symfony inject by type hint. In Laravel
  and Symfony it is on for everything; in CakePHP it is off until you add a
  `ReflectionContainer` (this build injects nothing); CodeIgniter has no container. In
  Gluo it is on where you turn it on, by a pattern rule or a binding, so the config files
  list exactly what the container can build. It is also a
  trade-off: an explicit binding is a plain lookup, while a class found by a pattern rule
  costs a `class_exists()` check and a pattern match each time it is resolved.
- **How separate the frontend is.** Gluo's `frontend/` can be deleted, or deployed
  elsewhere, without touching the API. The other four frameworks' screens are part of
  the application.
- **How many folders you start with.** Counting folders at the first level, without
  dependencies and hidden ones: CodeIgniter 4, Gluo 9, Laravel 9, Symfony official 10,
  CakePHP 10, Symfony template 12 (two of those are the template's own `docs/` and
  `frankenphp/`). CodeIgniter puts almost everything under `app/`.

## In one paragraph each

**Gluo** generated a working, documented and tested backend from the least input: one
SQL file became a model, four endpoints, their documentation and passing tests. What it left to write was
the delete endpoint, the price range and the whole screen, and it asks you to remember
one extra command after touching a route.

**Laravel** generated the least for the feature itself, together with CodeIgniter —
every body and every screen was written by hand — but what you write is short, and the
starter kit ships by far the most complete authentication and UI.

**Symfony** generated the whole CRUD including the screens and the SQL, at the price of
the most setup: access control by hand, unstyled pages, placeholder tests, and no soft
delete of its own — either hand-written with official packages only, or from a
community bundle on a community Docker template that needed fixing.

**CakePHP** is the closest to Gluo in direction: bake read the table and wrote a working
controller, the validation from the columns and four styled screens with paging and
sortable columns, so the feature itself cost almost nothing. The setup is where the work
went: no Docker of its own, a login wired by hand from the official plugin, and soft
delete from a community plugin; its test files were placeholders to rewrite.

**CodeIgniter** is the smallest: 5 production packages, a project that is almost all one
`app/` folder, and timestamps, soft delete, validation and pagination as settings of the
base model. Its generator writes only empty classes, so the migration, the controller
bodies and the screens are written by hand; Shield brings the login in two commands.
There is no Docker setup either.
